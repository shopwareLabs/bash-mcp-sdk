# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as scoped by the compatibility contract in `AGENTS.md`.

## [Unreleased]

### Changed

- `run_mcp_server` chains a consumer's pre-installed `EXIT` trap into server teardown in the direct call shape. The handler is no longer dropped: the server runs it after its own cleanup, on a clean exit and on a trapped signal alike. The handler's stdout goes to stderr, because stdout carries the JSON-RPC stream, and a handler that fails is logged rather than aborting the teardown or changing the server's exit status. The four signal handlers are still replaced.

## [5.0.0] - 2026-09-13

### Changed

- **Major**: sourcing `lib/mcpserver_core.sh` under a Bash below 4.1 is refused as the file is sourced. The message names the floor, the version found, and the platform's install command where one can be determined. Such a shell previously failed much later, inside `run_mcp_server`, with an error an MCP host reports as nothing more than a server that failed to start. The floor itself is unchanged and was already stated in `README.md` §Requirements.
- **Major**: sourcing the file with `jq` missing, or older than 1.7, is refused the same way. Such a server previously started and answered every request, while `validate_tool_arguments` returned the pre-3.0.0 verdict for a declared `integer`. That check needs the number-literal preservation jq added in 1.7.
- **Major**: sourcing the file with a `jq` that is present but cannot run is refused as its own case. The message names the path `command -v jq` resolved and reports that the binary did not answer `jq --version`. It leaves out the distribution-package warning, which applies only to a `jq` that reports a version below the floor.
- **Major**: both floors are read when the file is sourced, so `PATH` must select the intended Bash and `jq` at that point. A server script that repairs `PATH` after sourcing has to move that line above the `source`. An operator who cannot edit the script sets `PATH` in the host manifest's launch command instead. `README.md` §Requirements carries both forms.

## [4.0.0] - 2026-09-13

### Added

- `create_error_response` takes an optional fourth `data` argument, a JSON value carried into the error object's `data` field. Omitted or empty, the envelope is unchanged.
- `MCP_LOG_STDERR` (default `0`). Set to `1` and `log` mirrors each formatted line to stderr, on top of its existing file targets. stdout still carries only the JSON-RPC stream.
- `notifications/cancelled` is handled. A cancellation naming an in-flight `tools/call` stops that call, and no response is sent for its id. A cancellation naming nothing in flight is logged and dropped. The match requires `params.requestId` to be present, so a cancellation that omits it stops nothing.
- A tool may define an optional `tool_<name>_cancel` hook, which runs when its call is cancelled. It receives the call's original `arguments` JSON. When a signal tears the server down, the in-flight record holds the tool's group and name and no arguments. The hook then receives an empty string. A hook gets two seconds before it is killed; its exit status is logged rather than failing the call.

### Changed

- **Major**: `read_json_file` reads exactly one JSON document from its file and requires that document to be a JSON object. It returns 1 and writes nothing to stdout when the file does not hold exactly one JSON object. That covers a missing file, an empty file, more than one document, unparseable JSON, and a document of any other type. It previously substituted `{}` for a missing file and passed an existing file through unparsed, so a broken configuration looked like an empty one.
- **Major**: `initialize` and `tools/list` answer `-32603` when their configuration does not meet that rule. The message names the file they could not read. `initialize` previously answered with its defaults and `tools/list` with `{"tools": []}`. Neither answer let a client tell a degraded result from a correct one. `MCP_CONFIG_FILE` and `MCP_TOOLS_LIST_FILE` are effectively required, and each holds one JSON object.
- **Major**: `validate_tool_arguments` rejects a tools list it cannot read instead of skipping validation. The message is `Cannot validate arguments for <tool>: the tool list at <file> is missing or does not hold one JSON object.` A tools list that could not be read previously reported success, waving every declared constraint through for the caller.
- **Major**: a request whose `id` is present but is not a string or an integer is answered `-32600 Invalid Request`. It was previously dispatched or dropped. MCP requires a request id to be a string or an integer and forbids `null`, and a notification carries no `id` at all. A `null`, `true`, `false`, object, array or fractional-number `id` is therefore neither a request nor a notification, and is answered. For `true`, `false`, an object and an array the rejection is the only legal output rather than a strictness preference. A response must carry the request's own id, and a response id may only be a String, Number or Null. No valid success response for such a request can be constructed. The `id` is read by key presence and carried with `tojson` rather than with jq's `//`. That `//` mapped an absent id, a `null` id and a `false` id to the same output. A client sending `"id": false` or `"id": null` previously received no response and waited on a reply that never came. `"id": true`, an object or an array previously received a normal result for a request MCP does not define.
- **Major**: a tool now runs in its own process group, and that group is killed when the call ends. A child the tool leaves running behind it no longer survives the call, on success as much as on cancellation. A tool that must outlive its call has to detach into its own session.
- **Major**: a tool's stdin is `/dev/null`. It previously inherited the server's stdin, the JSON-RPC pipe.
- **Major**: a cancelled call's tool group is stopped with `SIGTERM`. Any member still running two seconds later is sent `SIGKILL`, and no response is sent for that id. A tool that dies on the `SIGTERM` is reaped at once. The sentinel that guards the group outlives the tool by design, and the grace period is measured against the group's members other than the sentinel. `notifications/cancelled` was previously ignored, so the call ran to completion and its response arrived.
- **Major**: a tool can no longer outlive the server, however the server dies. The server's main shell is the only writer on the lifeline, because a dispatch closes its inherited copy before a tool starts. A sentinel in the tool's process group therefore fires however the server was killed. That covers a signal to the server's pid alone and a signal to its whole process group, `SIGKILL` included. A wrapper that reaches the lifeline after the last writer is gone blocks on the open instead of starting its tool. No tool runs orphaned. The sentinel ignores `SIGTERM`, so the group `TERM` a cancellation sends cannot remove it before the server dies. That kill runs no cleanup. The in-flight record, the lifeline directory, the partial-line handoff file, and an in-flight call's output file with the sentinel pid recorded beside it can remain under `TMPDIR`. A server that goes down on a signal it can trap removes the output file and the sentinel pid file beside it. That removal is part of its teardown.
- **Major**: `run_mcp_server` installs `EXIT`, `INT`, `TERM`, `HUP` and `PIPE` traps, replacing any handler a consumer set on those signals. A signal to the server's whole process group takes effect at once. One sent to its pid alone mid-call takes effect after that call returns.
- **Major**: an id-carrying `notifications/initialized` now returns `-32601 Method not found`. The method is handled as the notification its name and its id-less form say it is. A message carrying an id is therefore an ordinary request for a method the server does not implement. 3.0.0 listed the method in its dispatch table and answered nothing for either form.
- **Major**: `lib/mcpserver_core.sh` requires Bash 4.1+, where it previously stated 4.0+. The file allocates file descriptors with `{var}` redirection, a 4.1 feature.
- A tool function runs with errexit disabled on every dispatch path, a direct call to `handle_tools_call` or `process_request` included. This matches 3.0.0 and is not a compatibility change.
- The grace a cancellation measures counts the tool group's live members other than the sentinel. It reads them from a full `ps -A -o pgid=,pid=` listing filtered in Bash, and the sentinel reads its own group id from the same kind of listing. A `ps` carrying `pid` and `pgid` columns is the one shape procps, BSD and BusyBox share. Alpine and BusyBox consumers therefore need no procps, and the SDK calls `pgrep` nowhere. A `ps` that fails falls back to the group's raw liveness. That count includes the sentinel, so the fallback spends the full two seconds before the `SIGKILL`. It delays a kill rather than dropping it, which is the slower direction.
- A signal that arrives while the shutdown teardown is already running is recorded rather than re-raised. The pass finishes: the cancel hook, the group `SIGKILL`, the removal of the in-flight call's files. The shell then dies by that signal.
- A partial line left on stdin when a client closes it mid-call is discarded, and only its length is logged. The exception is a partial line whose joined bytes already parse as JSON. That is the client's last request written without a trailing newline, and it is answered rather than discarded. An unterminated line that does not parse was previously parsed as a request and answered with a `-32700` parse error. The in-flight call's response still arrives first, and the server then exits. A line left incomplete when the call ends is carried out of the dispatch through a file. It is joined to the next line the read loop takes in. The call's response therefore reaches the client as soon as the dispatch returns rather than waiting on that line. The request the completed line forms is answered when its remaining bytes arrive. The join needs a line. A fragment the loop is holding when only an unterminated tail follows and stdin closes is dropped with that tail rather than dispatched. Nothing else can ever terminate it. A call that arrived mid-call and is replayed after it runs to completion without a cancellation window of its own. That keeps the replay from reading the client's stream.

### Fixed

- **Major**: a line that is not exactly one JSON document, or that is one document of a non-object type, no longer ends the server. Two shapes reached the crash. A line holding two or more JSON documents was accepted by the `jq -e '.'` parse gate, which reports only its last output. A client that omits the trailing newline on one message produces such a line. The `id` extraction then emitted one line per document, and the joined two-line `id` reached `create_error_response`'s `--argjson id`, which rejected it. The second shape was a document of a non-object type that the `jq -e '.'` gate accepted: `[1,2]`, `"x"`, `5` or `true`. Every field extraction yielded an empty string, and `create_error_response ""` passed that empty `id` to `--argjson`, which rejected it the same way. Either rejection returned non-zero out of `process_request`. That status ended the server at `run_mcp_server`'s plain `response=$(process_request "$line")` assignment, so a single such line from any client could stop it. The parse gate now admits exactly one JSON document of any type, so a line must hold one document. A line holding more is answered `-32700 Parse error` with a message naming the rule. A document that is not a JSON object is answered `-32600 Invalid Request` with a null `id` before any field of it is read. `null` and `false` are in that second class, and both are valid JSON. The `jq -e '.'` gate answered them `-32700` only because it exits non-zero on those two values.
- **Major**: a tools or configuration file holding one parseable document that is not a JSON object no longer ends the server. That covers a number, a string, an array, `true`, `false` and `null`. `handle_tools_list` ran `.tools // []` on it and `handle_initialize` handed it to `--argjson config`. Indexing a non-object errored, and the empty capture that followed made `--argjson` reject. The rejection returned non-zero out of `process_request`, which ended the server at the same assignment. This happened in the default shell mode, with no `set -o posix` needed. A server facing a `tools/list` against a file holding `5` answered neither that request nor the `ping` after it. Such a file is now answered `-32603` naming it. A `null` document read as an empty configuration by accident: indexing `null` yields `null`, and jq's `//` then took the defaults. It is answered with the rest.
- **Major**: a `tools/call` whose `params` is a number, a string, an array or `true` answers `-32602 Invalid params: expected an object` instead of `-32602 Invalid tool name: `. Under `set -o posix` it no longer ends the server. A present `null` or `false` `params` is normalized to `{}` before dispatch and keeps the `Invalid tool name: ` answer. `handle_tools_call` read `.name` and `.arguments` before checking the type of `params`. jq could not index a number, string, array or `true` with those keys. In POSIX mode bash inherits `errexit` into the command substitution those extractions run in, so the failure ended the whole server. `{"jsonrpc":"2.0","id":1,"method":"tools/call","params":5}` stopped it with no response, and the request that followed was never answered. The server survived in the default mode, but jq wrote its `Cannot index ...` diagnostics straight to the process's stderr, outside `log`. `params` is now gated as an object before either field is read, on the same footing as `process_request`'s request-object gate. The extractions cannot fail, and no diagnostic escapes the log. POSIX mode is not a configuration this file claims to support, but it no longer ends the server on this path.
- **Major**: a trailing fragment left on stdin at EOF is now answered instead of discarded wherever jq can read the bytes. Two sites decide whether such a fragment is answerable: the poll loop inside an in-flight call and the read loop. Both tested it with `jq -e '.'`, whose exit status comes from the truthiness of the output rather than from whether the input parsed. That dropped two classes. A fragment whose last document is `false` or `null`, both valid JSON, read as falsy. A whitespace-only fragment, holding no document at all, left the test with nothing to parse. A bare `false` or `null` fragment is now answered `-32600 Invalid Request`. A fragment holding several documents whose last is `false` or `null` is answered `-32700 Parse error`. A whitespace-only fragment is answered `-32700 Parse error`. Each is the same answer the identical bytes get when a newline follows them. The gate is now `jq empty`, which exits zero on any input jq can read, including one holding no document.

## [3.0.0] - 2026-09-03

### Changed

- `validate_tool_arguments` now enforces `minimum`, `maximum`, `exclusiveMinimum` and `exclusiveMaximum` against number-valued arguments. It previously read no range keyword. A schema declaring `minimum: 1` accepted an out-of-range value like `-1` and let it reach the tool function. **Major**: arguments that violate a declared bound now return an `isError` result instead of reaching the tool. Consumers should review every range declaration in their tools list against the values their clients send before bumping their pin. That means `minimum`, `maximum`, `exclusiveMinimum` and `exclusiveMaximum` alike.
- `validate_tool_arguments` now decides a declared `integer` from the number as jq renders it as well as from its value. It previously tested `val == (val | floor)` alone, and `floor` works in IEEE-754 doubles. At or above 2^52 (4503599627370496) the double spacing reaches 1. A fractional argument like `4503599627370496.5` was therefore already whole before the comparison, and it reached the tool function with its fraction intact. **Major**: a fractional argument at or above that threshold against an `integer`-typed property, `items.type`, or union member now returns an `isError` result. Values that are integers under JSON Schema stay accepted, including `1.0`, `1e2` and `1.5e3`. One gap remains. A value jq renders with an exponent keeps the old double-based verdict. A fractional value below the smallest subnormal double (`1.5e-400`) is therefore still accepted as an integer.
- Documented the `jq` version this behavior depends on: 1.7+. Below that floor, jq parses every number to a double and the rendered literal no longer preserves a fraction the double rounded away. This states an existing dependency; it does not add one.

## [2.0.0] - 2026-09-02

### Changed

- `validate_tool_arguments` now enforces a `type` declared as a list of alternatives (`"type": ["integer", "string"]`), on a property and on `items.type` alike. It previously treated a list-valued `type` as no constraint, so any value passed. **Major**: arguments a union-typed property accepted before this change can now be rejected with `isError`. Consumers should review before bumping their pin.

## [1.0.0] - 2026-09-02

### Added

- `lib/mcpserver_core.sh` — JSON-RPC 2.0 stdio loop, tool dispatch, `inputSchema` argument validation, dual-target logging.
- BATS suites covering the validator, the logging surface, and the guarantee that the file sources nothing and serves the protocol on its own.
- ShellCheck and BATS in CI.
